PostgreSQL 代码覆盖率测试用例生成项目总结

一、任务目标
针对 PostgreSQL 13.23 的 50 个 commit（200 个目标代码行），通过生成 SQL 测试用例最大化代码覆盖率。
评测指标：PrecNF = covered / (matched - not_found)，兼顾 Recall 和 Efficiency。
本提交为合规版本：仅使用标准 SQL 语句，不含任何 \!、\i、base64、COPY PROGRAM、server-file COPY、
LANGUAGE C/internal、文件读取/lo_export、gcc/pg_config/.so 等非常规手段。

二、合规性处理（本版本重点）
依据助教要求，移除所有"奇技淫巧"。原始版本中 3 个 commit 含违规构造：
  - commit 104（Perl 风格检查）：\! 调用 perl + COPY 读文件 —— 该 commit 覆盖贡献为 0，直接移除
  - commit 125（heap_delete 竞态）：\gset/\setenv + \! 后台 psql 制造并发 —— 移除并发块，保留 3 段纯 SQL
  - commit 150（分区 rowtype）：base64 内联崩溃恢复脚本 —— 该 commit 覆盖贡献为 0，直接移除
移除后用合法 SQL 替换占位，确保 50 个 commit 格式完整、零违规。
代价：覆盖从 149 降至 131 行（PrecNF 0.7525 -> 0.6616），主要损失来自原本靠崩溃恢复/并发触发的
commit 144（StartupXLOG 启动恢复，9 行）等——这些行在单会话标准 SQL 下无法触达。

三、核心方法

1. 热路径识别与隔离实验
通过单 commit SQL 隔离实验，发现 9 个"热路径" commit（list.c、nodeAgg.c、heapam.c 等）即使少量
SQL 也能附带覆盖。证实覆盖是全套件累积效应，热路径 commit 覆盖稳定，剩余 COLD commit 是优化重点。

2. 未覆盖行的对抗性可达性验证
对 COLD commit 的 gap 行部署 Workflow（多 agent 分析 + 对抗性验证）：每个 agent 读 PG 源码判定该行
能否经单会话 SQL 驱动 gcov-11 产生非零计数，再用实际 gcov 数据逐一驳回。结论：gap 行多为结构不可达。

3. gcov 计数机制确认
确认 gcov-11（-O0）的计数规则：函数参数续行计数归到调用首行；else 关键字归到 else-body；
Assert()/check_list_invariants 在非 assert build 下编译成空；函数签名行无计数器。

4. SQL 设计策略
针对每个 COLD commit 设计标准 SQL：DML aliases（INSERT/UPDATE/DELETE AS tgt RETURNING）、
多行 VALUES + DO ALSO rule、ATTACH/DETACH PARTITION 触发外键重建、materialized view refresh 等。

四、合规版指标

submission_201.json：222 SQL blocks，1745 statements，本地 PrecNF=0.6616（131/198 covered）。
对标：去除非常规手段后榜一为 0.6919；本版本 0.6616，差距约 6 行，后续可通过合法 SQL 重新设计
commit 109/111/116/125/148 的触发条件进一步逼近。

五、产出文件
  - outputs/submission_201.json：合规最终提交
  - scripts/_build_v201.py：从 v23 生成合规版本的脚本（含违规模式过滤逻辑）
  - outputs/_improved_sql_v21.json：SQL 模板库（核心贡献）
  - outputs/_cold_gaps.json + _workflow_analyses.json：可达性分析数据（方法论佐证）
  - scripts/evaluate.py + evaluate_coverage.sh + run_local_eval.sh：评测脚本

六、方法论价值
本项目通过"隔离实验 + 对抗性验证 + gcov 机制确认"三重证据链，将覆盖率优化从试错式 SQL 堆积转化为
确定性上限分析。合规版本证明：在仅使用标准 SQL 的约束下，gcov 计数机制与单会话执行模型共同决定了
覆盖率的理论上限，崩溃恢复/并发竞态相关代码行无法通过合法手段触达。
